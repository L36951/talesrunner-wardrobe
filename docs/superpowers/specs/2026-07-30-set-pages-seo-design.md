# 套裝頁：畀搜尋引擎索引嘅第一層

2026-07-30

由 `data/items.json` 預先生成 1,978 個套裝頁，令玩家喺 Google 搜套裝名嗰陣搵到呢個網。
呢個係分層 SEO 計劃嘅第一層；裝備逐件出頁留返之後按數據決定。

## 背景

個網而家得一條 URL。分享連結用 `#hash`，而 Google 唔會將 fragment 當成獨立頁面，
所以 16,001 件裝備嘅名由頭到尾冇喺任何 HTML 出現過。JS 渲染出嚟嘅 DOM 任何一刻
只有 `PAGE_SIZE=16` 張卡，即係就算 Google 行 JS 都只見到 0.1%。

競爭方面，[跑Online 維基（Fandom）](https://talesrunner.fandom.com/zh/wiki/%E8%A3%9D%E5%82%99)
有逐件裝備頁但覆蓋好散 —— `site:` 搜尋確認佢完全冇「聖言小丑」呢套。巴哈姆特有攻略文但唔係資料庫。
即係需求已驗證（wiki 存在、巴哈活躍、YouTube 有配裝教學片），但冇人補得齊。

先做套裝頁而唔係逐件裝備頁，因為套裝頁天然有 2–9 件裝備嘅內容，唔會薄；
而裝備描述中位數得 21 個字，逐件出頁有 39.4% 描述同人重複，係典型嘅大規模薄內容。

## 範圍

新增 build step 同 1,978 個靜態頁。`index.html` 個 SPA **完全唔郁**。

明確唔做：

- 逐件裝備頁 —— 等套裝頁索引率有數據先決定
- `vercel.json`（cache headers）同 WAF rate limit —— 另一個 PR，唔好塞埋
- `robots.txt` —— 另一個 PR，已定咗只擋 AI bots
- 改 `data/items.json` 或者配裝／能力值計算邏輯

## 1. 頁數同納入規則

由 1,980 個套裝定義推導：

| 步驟 | 數量 |
|---|---|
| `sets` 定義（全部有成員，零孤兒、零懸空 ID） | 1,980 |
| 剔走只有 1 件成員嘅套裝 | −2 → **1,978** |

成員數分佈（剔走單件之後）：

```
2件:236  3件:542  4件:521  5件:351  6件:288  7件:33  8件:4  9件:3
```

Build script 要 `assert` 呢個 1,978，數唔啱就 fail build —— 唔好 hardcode 頁數，
但要偵測到 `items.json` 重新生成之後結構有變。

### 男女變體各自一頁

154 個套裝名帶 `(男)` 或 `(女)`，其中 76 組成對。**每個 set 各自一頁，唔合併。**

呢點一開始設計錯咗。當時只睇「76 對之中 53 對套裝效果相同」就當佢哋係重複內容，
但套裝效果只係頁面一小部分，**成員裝備先係主體**，而成員完全唔同：

| 檢查（76 對） | 結果 |
|---|---|
| 成員裝備 ID 完全唔重疊 | 76 / 76 |
| 成員 icon 完全唔同 | 76 / 76 |
| 成員裝備名完全唔同 | 71 / 76 |

```
青花瓷套裝(男) → 青花瓷羽毛(男)、青花瓷長筒靴(男)、青花瓷套裝(男)
青花瓷套裝(女) → 青花瓷羽扇(女)、青花瓷高跟鞋(女)、青花瓷套裝(女)
```

羽毛對羽扇、長筒靴對高跟鞋 —— 連款式都唔同。加上可穿著角色亦唔同（男裝對男角色），
所以兩頁係實質唔同嘅內容，分開仲可以各自接「青花瓷套裝男」「青花瓷套裝女」呢類搜尋詞。

**互連而唔用 canonical。** 每頁喺顯眼位置連去對應嘅另一個性別版本。
唔可以落 `canonical` 指向其中一方 —— 咁做等於叫 Google 唔好索引另一頁，
正正抵消咗分開嘅目的。互連只係表達關係，同時多一條內部連結。

**5 對要留意**：`異世界(男)組合` 同 `異世界(女)組合` 呢類，成員名完全相同
（都叫「異世界鞋子／服裝／髮型」），只有 `setId` 同 icon 唔同。5 / 1,978 比例極低，
照分開處理，但如果日後 Search Console 見到呢批出現「重複網頁」狀態，
就針對佢哋喺標題同描述加返性別區分。

## 2. URL 同輸出結構

18 個套裝名會撞（`暗黑騎士套裝`、`天蠍座套裝` 等各有兩個），所以 URL 唔可以淨靠名。

```
/set/1042-青花瓷套裝
```

`setId` 保證唯一同穩定（名改咗 URL 都唔會斷），中文名幫排名。

輸出成目錄加 `index.html`：

```
set/1042-青花瓷套裝/index.html
```

**咁樣唔使開 `cleanUrls` 都有乾淨 URL。** 呢點重要：Vercel 嘅 `cleanUrls` 會將
`/google2085331cda3ef3a1.html` 改寫成 `/google2085331cda3ef3a1`，令 Google Search Console
嘅驗證檔 fetch 唔到、個 property 甩驗證。用目錄結構就完全避開呢個問題。

男女變體各自有自己嘅 `setId`，所以 URL 天然唔會撞（`/set/1259-青花瓷套裝-男`、
`/set/1260-青花瓷套裝-女`）。

Slug 規則：`（）()` 同空白轉 `-`，收尾嘅 `-` 剪走。中文字保留（Google 處理 percent-encoding 冇問題，
而且中文喺 URL 對中文 query 有幫助）。

## 3. 每頁內容

薄內容係「已檢索－未編入索引」嘅主因，所以每頁要有足夠獨特內容。

| 區塊 | 資料來源 | 備註 |
|---|---|---|
| `<title>` / `<h1>` | `sets[].name` | 標題要含「套裝效果」「能力值」等字 |
| `meta description` | 由套裝效果同件數生成 | 每頁唔同 |
| 套裝效果表 | `sets[].stats`（`[文字, 顏色]` 陣列） | **304 個套裝冇效果，要 fallback 文案** |
| 成員裝備 grid | `items` 入面 `setId` 相符者 | 圖、名、部位、逐件能力值 |
| 著齊全套合計能力值 | 由成員 `stats` 加總 | |
| 男女對應版本連結 | 適用於 76 對（152 頁） | 互連，唔落 `canonical` |
| 可穿著角色 | 成員 `blockedFor`／`wearGroup`／`character` 交集 | |
| 「立即試身」深連結 | 現有 `#hash` 格式 | 見下 |
| 相關套裝 | 見下方排序規則 | 內部連結，每頁固定 8 條 |
| JSON-LD | `schema.org` 結構化資料 | |

`equipmentType` 分佈：`role` 1,166、`avatar` 814。呢個決定深連結入邊個裝備層。

### 相關套裝嘅排序規則

「效果相近」要有明確定義，否則每頁連出去嘅嘢會唔穩定，內部連結圖亦唔可預測。
候選係同 `equipmentType` 嘅所有其他套裝，按以下次序排，取頭 8 個：

1. 共用嘅套裝效果條數（`sets[].stats` 逐條文字比對）由多到少
2. 成員件數差距由細到大
3. `setId` 由細到大（保證同一份 `items.json` 每次 build 結果一樣）

304 個冇套裝效果嘅套裝第 1 項一律係 0，會跌落靠件數同 ID 排 —— 可以接受，
但要確保佢哋唔會全部互相連埋一舊，變成一個同其他頁斷開嘅孤島群。
Build script 要檢查每個套裝頁最少有一條**入邊**連結（即係有其他頁連過嚟），
冇嘅話 fail build。

### 圖片路徑

`index.html` 用 `ICON_BASE='assets/itemimage/'` 呢個相對路徑。套裝頁喺 `/set/<slug>/` 之下，
相對路徑會斷，所以生成嘅 HTML 一律用**絕對路徑** `/assets/itemimage/<icon>`。

每個 `<img>` 要有 `alt`（裝備名）—— 圖片搜尋係額外流量來源，而 `assets/` 唔會被 robots.txt 擋。

### 試身深連結

重用 `buildShareUrl()` 嘅格式，唔加任何新機制：

```
/#v=1&char=<預設角色>&avatar=<件1,件2,...>&role=<...>&view=<avatar|role>
```

按 `equipmentType` 決定啲件放 `avatar=` 定 `role=`，`view=` 跟同一個值。

`char=` 唔可以求其填 —— 揀錯角色會令個連結一打開就有裝備著唔到。規則：
喺 `characters` 入面按現有次序，揀**第一個唔喺任何成員 `blockedFor` 入面、
而且通過所有成員 `wearGroup` 限制**嘅角色。搵唔到就 fallback 落
`DEFAULT_CHARACTER`，同時喺頁面標明「呢套裝備冇角色可以著齊」——
呢個情況本身係有用資訊，唔應該靜靜哋隱藏。

呢條連結係套裝頁最大嘅差異化 —— Fandom wiki 永遠複製唔到。

## 4. 生成 script

`scripts/build-seo.mjs`，純 Node，唔引入 framework。

```
讀 data/items.json
  → 建 setId → 成員 的索引
  → 套用納入規則（成員 >=2 件）
  → assert 頁數 === 1978
  → 每個套裝生成 set/<id>-<slug>/index.html
  → 生成 sitemap-sets.xml 同 sitemap-index.xml
```

Vercel build command 行呢個 script。輸出目錄照舊係 repository 根目錄。

HTML 要 escape。`index.html` 而家 13 處 `innerHTML` 直接插 `${item.name}` 冇 escape，
目前 `items.json` 冇 `<`、`>`、`"` 所以安全，但生成 script 唔可以繼承呢個假設 ——
下次 regenerate `items.json` 出現帶引號嘅裝備名就會爆。

## 5. Sitemap 同內部連結

```
sitemap-index.xml
└── sitemap-sets.xml     1,978 條（遠低於 50,000／50MB 上限）
```

分開檔案係為咗**逐層量度索引率**。Search Console 可以逐個 sitemap 睇，
第二層加入之後就知邊層收得好、邊層拖後腿。

內部連結：任何套裝頁距離首頁 ≤3 下 click。首頁加一個套裝索引入口 →
按 `equipmentType` 同分類分組嘅列表頁 → 套裝頁。加上每頁 6–8 條「相關套裝」互連，
令 1,978 頁織成一張圖而唔係 1,978 個孤島。深度過大嘅頁基本上唔會被索引。

## 6. 成功指標

4–8 星期之後睇 Search Console `sitemap-sets.xml` 嘅索引率：

- **>70%** → 做第二層（2,340 個有獨特描述兼有 stats 嘅裝備頁）
- **40–70%** → 先改善每頁內容同攞反向連結，唔好加頁
- **<40%** → 停手重新評估，加頁只會令情況更差

要留意「已發現－未編入索引」同「已檢索－未編入索引」係兩個唔同問題：
前者係爬取需求不足（要反向連結），後者係質素判斷（要改內容）。

100% 索引唔存在，唔好當佢係目標。

## 7. 風險

**反向連結係最弱嗰環。** 爬取需求主要由外部連結決定，而呢個網幾乎零外部連結
（只有 `kennylaisk.com` 個 portfolio 連過嚟）。冇呢樣，其餘全部做足都會卡喺
「已發現－未編入索引」。實際做法：巴哈姆特哈啦板、HK Facebook 社群、Threads、
YouTube 教學片描述欄。呢個係人手工作，唔喺呢個 spec 範圍，但唔做嘅話個 spec 嘅效果會大打折扣。

**資料公開唔可逆。** Repo 係 public，`items.json` 同 16,051 張圖已經喺公開 git history。
套裝頁會將 7,955 件裝備嘅資料以 HTML 形式再公開一次，但**實際新增曝露接近零**。
呢個交易已經同用戶確認過。

**`items.json` 重新生成會影響頁數。** Script 嘅 assert 會捕捉到，但更新 pipeline 之後
要記得重新 build 同重交 sitemap；URL 用 `setId` 所以名改咗都唔會斷連結。
